#Overview

A verified user manual, architecture guide and audit for GoshCoder 0.6.0.

#What GoshCoder is Verified at runtime

GoshCoder is a terminal coding agent written in Rust. You type a request; a large language model answers and, when tools are enabled, reads and edits files in your project and runs shell commands for you. It is a reimplementation of the TypeScript agent pi: it uses pi's session file format, credential file format, tool names and model catalog on purpose, so the two tools can share data.

Interfaces

A fullscreen terminal interface (Ratatui), a plain line-mode chat for pipes and screen readers, and a one-shot run command for scripts.

Providers

45 provider definitions and 1,256 bundled models over nine wire protocols, plus two self-hosted gateways (OmniRoute, Tailscale Aperture). Logins for eight subscription providers.

Tools

read, write, edit, ls, grep, find, bash, web_search, plus optional desktop control, image generation and gateway connector tools.

Built-in extensions

Planner (plan review in the browser), Ralph (long-running loops), BTW (side questions), Grok CLI accounts and image generation, Meta Muse Code.

#Current limitations at a glance Source inspection

  • No plugin host, package manager, LSP, MCP server management or custom models.json loading (pi has these).
  • Cloudflare AI Gateway and Workers AI models are listed but every request goes to an unusable URL (finding F-03).
  • Amazon Bedrock works with static keys and the Bedrock bearer token only; SSO, container and web-identity credentials are detected but not used (F-19).

#Getting started

Install GoshCoder, connect a model provider and run your first session.

#System requirements Source inspection

  • Operating system: Linux (x86_64, arm64; static musl builds), macOS (Intel, Apple Silicon), Windows 10/11 (x64; ARM64 runs the x64 build under emulation).
  • Terminal: any terminal with 24-bit colour for the fullscreen interface; at least 20×8 cells (below that it shows “Terminal is too small”). The sidebar appears at 96 columns and wider. A terminal with the kitty keyboard protocol makes Shift+Enter and Ctrl+Shift+P work.
  • An account with a model provider (subscription login or API key), or a local OpenAI-compatible gateway.
  • Optional tools: git (faster grep/find, Planner code review), gh (/share, Planner PR review), computer-use-linux (desktop control, Linux only), $VISUAL/$EDITOR (/prompt edit).
  • Building from source: current stable Rust (the code uses let-chains; tested with rustc 1.97.0). rust-toolchain.toml selects stable with clippy and rustfmt.

#Install Source inspection

Linux and macOS

curl -fsSL https://raw.githubusercontent.com/goshitsarch-eng/goshcoder/main/install.sh | sh

Options (pass them with sh -s -- … when piping): --dir <path>, --version <tag>, --from-source, --no-modify-path. The same can be set with GOSHCODER_INSTALL_DIR, GOSHCODER_VERSION and GOSHCODER_FROM_SOURCE=1. The default directory is the first of ~/.cargo/bin or ~/.local/bin that is already on PATH, else ~/.local/bin.

curl -fsSL https://raw.githubusercontent.com/goshitsarch-eng/goshcoder/main/install.sh | sh -s -- --version v0.6.0 --dir "$HOME/bin"

Windows (PowerShell)

irm https://raw.githubusercontent.com/goshitsarch-eng/goshcoder/main/install.ps1 | iex

The PowerShell installer takes PowerShell-style parameters: -InstallDir (default %LOCALAPPDATA%\Programs\goshcoder), -Version, -FromSource, -NoModifyPath. Through irm | iex you cannot pass them; set GOSHCODER_INSTALL_DIR or GOSHCODER_VERSION first, or download the script and run it.

What the installers do

  1. Download goshcoder_<version>_<os>_<arch> (.tar.gz, or .zip on Windows) and checksums.txt from the GitHub release.
  2. Check the SHA-256. The PowerShell installer refuses a missing or mismatched checksum. install.sh also refuses a mismatch, but installs without checking when neither sha256sum nor shasum exists (F-38).
  3. Replace the binary in place, run goshcoder version, and offer to add the directory to your shell profile (only with a terminal on stdin; curl | sh just prints the line to add).

Fallback to source. If any download step fails, both installers build the current default branch from source instead, even if you asked for a specific --version (F-23). Read the warnings it prints.

From a checkout

git clone https://github.com/goshitsarch-eng/goshcoder
cd goshcoder
make build      # release binary in bin/goshcoder, stamped with git describe
make install    # copies it to ~/.cargo/bin (or $CARGO_INSTALL_ROOT/bin)

Verified here: make build produced bin/goshcoder reporting goshcoder v0.6.0-27-g3870a05. A plain cargo build reports 0.6.0.

#First launch Verified at runtime

Run goshcoder in your project directory. With no credentials it opens fullscreen chat with the Add provider picker already open.

  1. Type to filter the list (for example deeps), use ↑/↓, and press Enter.
  2. For an API-key provider, paste the key and press Enter. The key is masked and stored in ~/.goshcoder/agent/auth.json with mode 0600.
  3. For a subscription, choose the login method; the sign-in address (or device code) is shown and also copied to your clipboard through the terminal. See Logging in.
  4. The first successful login selects that provider's default model. The next thing you type is a prompt.

To leave, type /exit, or press Ctrl+D on an empty editor. If the session was saved, GoshCoder prints Resume with: goshcoder chat -continue.

#Quick-start tutorial Verified at runtime

This walk-through uses the real commands; the screenshots come from a session against a local test gateway, so the model replies are canned.

  1. Start in your project. cd ~/code/todo-app && goshcoder. The sidebar shows the model, context use and workspace.
  2. Ask something. Type Please list files in the project and press Enter. While the reply streams, the status bar shows a spinner and elapsed time; typing and pressing Enter now steers the reply instead of starting a new one.
  3. Watch tool calls. Each tool call becomes a card (✓ ls ., ✓ read README.md). Press Ctrl+O to expand or collapse their output.
  4. Switch model. Press Ctrl+L (or type /model), type part of a name, press Enter. The choice is remembered for next time.
  5. Name the session. /name Due dates spike. Sessions are saved automatically under ~/.goshcoder/agent/sessions.
  6. Come back later. goshcoder -continue reopens the latest conversation in this directory; goshcoder -resume lets you pick one.

For one-off scripted use there is goshcoder run. Note that run has no tools unless you pass -tools:

goshcoder run -m anthropic/claude-sonnet-5 -tools "explain this repository"

#A tour of the interface Verified at runtime

Fullscreen chat is the default when GoshCoder runs in a terminal. It draws on the terminal's alternate screen, so your scrollback is untouched when you leave.

  1. Header — the session name, or the first message, or “interactive session”.
  2. Transcript — your messages on a grey bar, replies rendered as Markdown, tool calls as cards (● running, ✓ done, × failed), notices (i Notice), errors (× Error) and echoed commands (◇ Command). It is anchored to the bottom and capped at 124 columns wide.
  3. Composer — where you type. It grows to eight lines. Type / for the command palette.
  4. Status bar — ● Ready, or a spinner with the current activity and elapsed time, and the keys that apply right now.
  5. Sidebar (96 columns and wider) — session title, model, thinking level and mode, whether the session is being recorded, a context-usage bar with tokens and cost, an Activity block (turns, tools, changed files, last tool), the Planner checklist when there is one, and the workspace path.

#Typing, sending and steering Verified at runtime

  • Enter sends. Ctrl+J inserts a newline (Shift+Enter and Ctrl+Enter too, on terminals with the kitty keyboard protocol). Pasted text is never sent line by line; pastes over 20 lines are shown as [pasted N lines].
  • While a reply is streaming, Enter steers it: the message is delivered to the model at the next opportunity. Alt+Enter instead queues a follow-up for after the reply. Queued messages appear above the composer as ↳ queued …; /queue lists them.
  • Esc while streaming aborts the reply. Queued messages are put back into the editor so nothing runs after an interrupted turn; the partial reply is kept and marked “Interrupted”.
  • Esc on a draft clears it; ↑ brings it back. ↑/↓ also move between lines and through history.
  • Editing works by grapheme, so emoji and accented letters are never split.

#Choosing a model and reasoning level Verified at runtime

Models are named provider/model, for example anthropic/claude-sonnet-5. A bare id works when only one configured provider has it.

  • At startup the model is chosen from, in order: -m; the GOSHCODER_MODEL environment variable (an unknown value stops chat from starting, F-47); the model you last picked (stored in ~/.goshcoder/agent/default-model); the first configured provider in a built-in preference list (OpenAI Codex, Anthropic, Kimi, OpenAI, Azure, DeepSeek, Grok CLI, xAI, Meta, Meta Muse, Google, Vertex, Z.AI, Moonshot, MiniMax, Mistral, Xiaomi, Copilot, OpenCode, Bedrock, Cloudflare); OmniRoute's auto; any model of the first configured provider.
  • In chat use /model, Ctrl+L, or Ctrl+P to cycle. A choice made this way (or by a first login) is remembered; -m is not.
  • Reasoning: levels are off, minimal, low, medium (default), high, xhigh, max. Each model supports a subset, and the requested level is clamped to it; /thinking and Shift+Tab offer only supported levels. -thinking <level> sets it at startup.

List models from the command line:

goshcoder models              # models of configured providers
goshcoder models anthropic    # every model of one provider

#Logging in and adding API keys Verified at runtime

Credentials are kept in ~/.goshcoder/agent/auth.json (mode 0600 on Unix), in pi's format. Adding one login never removes another.

Inside chat

/login opens the picker. Providers with both a subscription login and an API key have two rows; /login <provider> key goes straight to the key prompt. The login runs inside the interface; Esc or Ctrl+C cancels.

From the shell

goshcoder providers                 # what is configured, and how to set up the rest
goshcoder auth login anthropic      # browser or copy-code
goshcoder auth set openai           # store an API key (prompted, not echoed)
goshcoder auth list                 # stored credentials (names only)
goshcoder auth logout anthropic     # remove a stored credential

auth logout removes only the stored entry; a key in an environment variable keeps the provider configured.

File tools are confined to the workspace (the directory you started in, or -C <dir>): paths outside it and symbolic links pointing out are refused, and writes to the same file are serialised. #Long conversations and compaction Verified at runtime

When a conversation approaches the model's context window (within clamp(window/5, 2048, 16384) tokens of it), GoshCoder summarises the older part before the next prompt and keeps roughly the last 20,000 tokens. /compact [focus] does the same on demand; the optional text tells the summariser what to keep.

Compaction cannot be interrupted, and queued messages are dropped when it finishes (a notice says so). If the provider fails while summarising before a prompt, the prompt is not sent (F-11); switch model or wait and retry.

#Errors and automatic retries Verified at runtime

Transient provider failures (HTTP 429 and 5xx, rate limits, overloads, timeouts, dropped streams) are retried up to three times after 2, 4 and 8 seconds. The status bar counts down; Esc cancels the wait. Other errors appear as × Error with the provider's message; quota and billing errors are not retried.

Streams time out after 300 seconds without data, and connections after 30 seconds.

#Sessions: saving, resuming and naming Verified at runtime

Chat records every conversation automatically to ~/.goshcoder/agent/sessions/<workspace>/<timestamp>_<id>.jsonl (pi's v3 format, mode 0600). A conversation with no reply is not kept. run records only with -continue, -session or -name.

Only one process can write a session at a time: a lock file next to it is refreshed every 2 seconds and considered stale after 20. A second window opening the same session gets it read-only.

#Rewinding, branching and cloning Verified at runtime

  1. /tree lists your messages as numbered rewind points, with labels and other branches.
  2. /fork N rewinds to just before message N. In fullscreen, message N is put back in the editor so you can change it and press Enter to take the conversation another way. /fork on a point from another branch jumps back to that branch.
  3. /label N name names a point; labels show in /tree. Labels cannot be removed from chat (F-35).
  4. /clone copies the current branch into a new session file and switches to it.

All of this needs a recorded session and an idle agent.

  • HTML is a single page with no scripts and a policy that blocks all network loads. It includes Markdown, thinking blocks and collapsible tool cards with full arguments and results, from the current context (after the last clear).
  • Markdown includes user and assistant text and tool names, but no tool output or thinking.
  • JSONL is the complete, lossless file (every branch and cleared message).
  • Exports are written with mode 0600 and overwrite existing files. The target directory must exist.

Bare /export writes goshcoder-session-<id>.html into the project directory, where it can be committed by accident (F-07). Give it a path outside the repository.

It uploads the HTML page as a secret gist through the GitHub CLI (gh must be logged in). Secret gists are unlisted, not private. Set GOSHCODER_SHARE_VIEWER_URL to print a viewer link.

#Backup and recovery Source inspection

  • Everything: copy ~/.goshcoder/agent/. It holds auth.json (secrets — protect the copy), sessions, prompts, skills and gateway settings.
  • One session: goshcoder sessions export <id> file.jsonl is lossless; restore with sessions import.
  • Prompt templates: goshcoder prompts backup writes goshcoder-prompts-YYYY-MM-DD.tar.gz; goshcoder prompts restore <archive> brings them back, skipping existing names unless --overwrite; --dry-run previews.
  • After an accidental /clear: the cleared messages are still in the file. Export the JSONL to keep them, or use /tree and /fork N on the last message before the clear (this restores the conversation up to just before that message). sessions show --full shows only one-line previews.
  • Damaged files: a half-written last line is ignored (and trimmed when the session is next opened for writing); other unreadable lines are skipped with a notice. A file with a broken header, or over 256 MiB, cannot be opened and disappears from listings.
  • Durability: each entry is appended as it happens and synced to disk at the end of each prompt's run. A reply that was still streaming when the process died is lost; a power cut can lose the last entries.

Session files contain everything the agent read and every command's output, with no redaction. Use -no-session for work that should not be written down.

#Ralph: long-running loops Verified at runtime

A Ralph loop repeats a task over many iterations: each iteration the model works, updates .ralph/<name>.md, and calls ralph_done to continue, until it replies <promise>COMPLETE</promise> or reaches the iteration limit (default 50).

/ralph start duedates Add due dates to todo items [--max-iterations 20]

/ralph list [--archived]

Loop files live in the workspace's .ralph/ directory. Ralph is on by default in chat; -ralph=false turns it off. #Planner: plan first, then review in the browser Verified at runtime

#What happens when you press Enter Verified at runtime

  1. The key handler returns Action::Submit; submit_interactive_input decides between a new prompt, steering (a reply is running) and a follow-up (Alt+Enter). Templates and skills are expanded first.
  2. begin_interactive_turn spawns a thread that calls turns::run_prompt: automatic compaction if near the limit, then Agent::prompt.
  3. run_loop records the message, polls steering, and calls the responder with the system prompt, messages and tools (cache retention short).
  4. catalog_assistant_responder resolves the model and credentials on every turn (refreshing OAuth under the auth lock), applies gateway rewrites, builds the protocol request and streams it. A connect timeout of 30 s and an idle-read timeout of 300 s apply; there is no whole-request deadline.
  5. Stream events become MessageUpdate events. The interface's listener pushes them into a channel; the event loop redraws when something changed or every 100 ms while busy.
  6. Tool calls are validated and run in parallel threads (sequential for Ralph, Planner, desktop and connector tools). Results go back in the next request until a reply has no tool calls. Tool calls in a reply cut off by the length limit are never run.
  7. The session recorder appends each finished message to the JSONL file and syncs it at the end of the run.
  8. finish_run retries retryable errors (2, 4, 8 s), compacts and retries once on context overflow, and runs queued follow-ups.

#State, concurrency and cancellation Verified at runtime

  • Agent state is one mutex-protected struct; listeners are never called with it held, so they can call back in. Agent::state() clones the whole transcript and is called on every redraw.
  • Threads: one per prompt, one per tool call in a batch (unbounded), two pipe readers per process, one-shot background refreshes at session start (OmniRoute health, Aperture sync, Meta Muse models), a session-lock heartbeat, and a termination watchdog.
  • Cancellation is a shared flag per run. bash polls it every 10 ms and kills its process group; HTTP reads poll every 25 ms; the retry wait wakes on abort. Compaction and in-flight web searches cannot be cancelled.
  • Locks on disk: auth.json.lock (OS advisory lock, 60 s wait); session .lock files (2 s heartbeat, 20 s stale); Grok account vault lock (30 s stale).
  • Signals: SIGTERM/SIGHUP abort the turn, close the session and exit with 128+n; a watchdog forces exit after 5 s (TERM) or 0.5 s (HUP). Verified: SIGTERM during a streaming reply exited 143 and saved the interrupted turn.

#Security and privacy boundaries Verified at runtime

  • Trust boundary: the workspace is untrusted input. Its AGENTS.md is quoted as context; its SYSTEM.md replaces the system prompt; its prompt templates become commands (F-01, F-06).
  • File tools refuse paths and symlinks leading outside the workspace, best-effort (F-28). bash runs with your privileges and environment.
  • Network: requests go to the configured provider, plus: OAuth endpoints during login; Exa/OpenAI/Kagi for web search; x.ai/cli/stable for the Grok CLI version; models.dev for Aperture; GitHub through gh for /share. Nothing is sent elsewhere; there is no telemetry.
  • Local servers (OAuth callbacks, Planner review) bind to 127.0.0.1, check the Host header, use no-store and CSP headers, and validate state or a CSRF token (OpenRouter's callback uses a random path instead). Any local user can reach them (F-54).
  • Secrets are stored 0600 and never echoed; credential types have no debug output. Session transcripts are not redacted.
  • Exports are script-free HTML with default-src 'none'; verified: 0 <script> tags and that CSP in an exported file.

  1. Make sure cargo audit is clean (it is not at this revision, F-04).
  2. Push the tag or release/vX.Y.Z branch.
  3. After publishing, merge any release branch back and bump the version in Cargo.toml, Cargo.lock, the Makefile and both installers (not done after v0.6.0, F-46).
